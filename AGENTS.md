## Границы работы

- Работать только в текущем репозитории LEXICON и только над явно согласованной задачей. Не переходить самостоятельно к следующему этапу.
- Не читать и не изменять другие локальные проекты. Не обращаться к другим Cloudflare-аккаунтам или Worker, включая внешние зависимости frontend.
- Единственный разрешённый аккаунт проекта: `e7dd176c5580b561da2048b23ed5f6c0`; Worker: `lexicon-worker`; D1: `lexicon-db`, binding `DB`, ID `6e63edd9-166b-400a-a644-caf474dc0ce6`.
- Production deploy, любые операции с D1 (включая запросы, экспорт, миграции, локальные операции и изменение схемы/данных) и изменение секретов требуют отдельного явного разрешения пользователя на соответствующую операцию. Не считать разрешение на редактирование кода разрешением на эти действия.
- Создание/удаление облачных ресурсов и изменение облачных переменных или bindings требуют явного согласования. Не выполнять сетевые действия с побочными эффектами для проверки документации.
- Не выполнять commit, push или tag без разрешения. Для CP-001 пользователь явно разрешил commit `CP-001: Import LEXICON backend and add PWA update`, tag `cp-001`, push и публикацию frontend после успешных проверок. Это не разрешает backend deploy, D1, секреты или CP-002.

## Исходники, секреты и проверка

- Карта архитектуры: `docs/PROJECT.md`; журнал: `docs/CHECKPOINTS.md`.
- Исходники Worker, конфигурация без секретов и описание каждого согласованного изменения должны сохраняться в Git и публиковаться в origin GitHub после разрешения на commit/push. До push прямо указывать, что версия ещё не сохранена в GitHub.
- Не записывать значения ACCESS_TOKENS, ключей API, паролей и токенов в отслеживаемые файлы, отчёты, логи или сообщения. Не выводить полные API-ответы с переменными. Применять белый список полей.
- Локальные секреты допустимы только в игнорируемых файлах, например `backend/.dev.vars`, когда это согласовано. Примеры файлов должны содержать только заглушки. Если импортируемый код содержит встроенный секрет, остановить импорт и сообщить без раскрытия значения.
- Сохранять логику импортированного Worker без изменений, если задача не разрешает её менять. Выполнять проверки соразмерно изменению; минимально для JS — `node --check`.
- GitHub не доказывает фактическое состояние Cloudflare. Отдельно указывать дату и способ облачной проверки; непроверенное обозначать явно.

## Checkpoints

- Каждый согласованный завершённый этап оформлять отдельным коммитом `CP-NNN: краткое понятное описание` и тегом `cp-nnn` на тот же коммит, только после разрешения.
- Перед выбором номера проверить всю доступную историю, локальные теги и теги origin; при неполной истории или недоступности origin отметить ограничение. Повторно проверить номер непосредственно перед созданием checkpoint.
- Не переименовывать старые коммиты, не переписывать историю, не передвигать существующие теги. Rollback преимущественно через согласованный `git revert`; без force push. Откат Git не меняет Cloudflare автоматически.
- В журнале описать причину, состав изменения, проверки, ограничения и отдельно состояние публикации GitHub и production. Предложенный checkpoint не называть созданным.

## Перед и после production deploy

- Получить отдельное явное разрешение. Для backend deploy непосредственно перед публикацией проверить аккаунт, имя Worker, актуальные bindings, переменные, имена секретов и их сохранение; не раскрывать значения. Проверить соответствие D1 ID. Не создавать заменяющие ресурсы. Frontend публикуется отдельно через GitHub Pages; это не должно запускать deploy backend.
- Подготовить и проверить точную версию публикуемых файлов: commit/tag, чистоту рабочего дерева или явно согласованный diff, список файлов, хеш Worker и эффективную конфигурацию сборки. Конфигурация находится в `backend/wrangler.jsonc`; не публиковать frontend вместо backend.
- `keep_vars: true` помогает сохранить отсутствующие в конфигурации облачные vars, но не заменяет проверку bindings, секретов и итоговой конфигурации. Не переносить ACCESS_TOKENS в Git.
- После разрешённого deploy проверить фактическую активную версию Cloudflare и согласованный smoke test. В документации записать дату, commit/tag, хеши, deployment/version ID, результат и ограничения. Не считать успешный push доказательством deploy. Запись результата сохранять в GitHub отдельным согласованным коммитом; существующий checkpoint-тег не передвигать.

## Frontend PWA

- Изменять существующий статический frontend в корне. Перед checkpoint/push запускать `npm run build:frontend` и `npm run check:frontend`; генерируемые `sw.js` и `frontend-release.js` включать в тот же коммит. Backend и документация не должны менять frontend release ID.
- Update — только для действительно ожидающего frontend Service Worker или активированной в другой вкладке новой версии. Активация и перезагрузка только после нажатия пользователем; не добавлять агрессивный polling.
- Сохранять текстовые черновики в sessionStorage этой вкладки; при невозможности сохранения или при неподдерживаемой незавершённой работе блокировать обновление с объяснением и повтором. Не кэшировать API, авторизованные запросы или пользовательские данные через SW.
- GitHub Pages сейчас публикует main из корня. `_config.yml` исключает backend и служебные файлы из сайта. Перед изменением публикации перепроверять фактические настройки. Не считать локальную эмуляцию standalone доказательством теста установленной PWA или физического iPhone.
