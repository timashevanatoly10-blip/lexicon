# LEXICON MCP — исходный план проверок

Связан с [историческим планом](MCP_INTEGRATION_PLAN.md). CP-002 использует opaque
OAuth tokens (не JWT/JWKS): resource, срок, scope и привязка owner проверяются
сервером в D1. Реализованные проверки — `tests/mcp.cjs`, результаты —
[CHECKPOINTS.md](CHECKPOINTS.md), инструкции — [MCP_CONNECT.md](MCP_CONNECT.md).
Описанные ниже сценарии являются исходной матрицей, а не заявлением, что каждый
пункт проверен через реальный интерфейс ChatGPT.

## Проверки без production

1. MCP lifecycle: initialize, initialized, tools/list, tools/call; ровно пять
   согласованных tools, корректные schemas/structuredContent, readOnly/write hints.
   Проверить Worker-совместимый Streamable HTTP; неизвестный метод/инструмент,
   версия протокола, неправильный JSON, oversized body и таймауты.
2. Auth: discovery, PKCE, точный redirect/resource, допустимый issuer/JWKS,
   audience, exp/nbf, scopes, отзыв grant и reconnect. Отдельно проверить auth
   handshake/list/tools согласно выбранному режиму подключения, без приватных
   данных в discovery. Подпись без проверки claims недопустима.
3. Изоляция на синтетических владельцах A/B: чужой dictionary_id, подмена owner
   в arguments, токен иного audience, sub без mapping, одинаковый sub у иного
   issuer. В результатах и курсорах не раскрывать чужие записи или owner hash.
   Не использовать реальные другие проекты/аккаунты как тестовые fixtures.
4. Read-only scopes разрешают list/get/search и запрещают create/add. Невалидный
   токен даёт 401; scope недостаточен — 403. Не требовать API key в тексте чата.
5. Словари: пустой список, одинаковые названия, отсутствующий/чужой ID,
   pagination, спецсимволы и длинные строки. Не выполнять выбор первого кандидата
   и не создавать словарь при 404 add_words.
6. Batch: 1/50/51 слово, пустой перевод/word, нулевой batch, размер тела,
   Unicode/регистр/пробелы, pump/Pump/PUMP, насос/НАСОС, акценты/пунктуация,
   run/running и разные POS одного слова. Зафиксировать согласованную семантику.
7. Дубли: внутри batch, существующий canonical word, параллельные MCP-записи
   и параллельная REST-запись. Существующие перевод/meta не перезаписываются.
8. request_id: повтор того же payload, другой payload с тем же ключом, другой
   владелец с тем же ключом, параллельные одинаковые запросы. Потеря ответа после
   commit, откат при сбое БД, срок хранения idempotency и повтор за его пределами.
   Доказывать отсутствие частичного batch, а не только совпадение счётчиков.
9. Регрессия старого REST на фикстурах: чтение, legacy auth и owner-фильтры,
   create/upsert-контракт, meta, формат duplicate; удаление не публиковать в MCP.
10. Рендер карточек: список, center.parts/meanings/examples, пустые side panels,
    IPA-placeholder, XSS/HTML, prompt injection в словах/note. MCP-вызов не должен
    сам обращаться к OpenAI/DeepL или создавать публичные ссылки.
11. Private API не попадает в PWA-кэш, MCP не вызывает ложную кнопку Update.
    Данные, добавленные MCP, видны после штатной загрузки словарей из общей базы;
    различать обновление данных и версию frontend.

Первая фаза — моки. Локальная/remote D1, создание схемы, миграции и реальные записи
нуждаются в отдельном разрешении; нынешнее разрешение на чтение sqlite_schema
не распространяется на запись тестовых данных. Перед будущей миграцией — аудит
конфликтов без автослияния и согласованная стратегия сохранения данных.

## Реальные команды из ChatGPT после отдельного подключения

| Команда | Ожидаемое поведение |
|---|---|
| «@LEXICON Покажи мои словари, ничего не меняй» | list_dictionaries; названия, ID, количество слов, pagination |
| «@LEXICON Открой словарь с ID …» | get_dictionary; только выбранный владелец/словарь |
| «@LEXICON Создай словарь “MCP — проба” с описанием “Проверка подключения”» | create_dictionary, подтверждение write и реальный ID; при том же названии уточнение |
| «@LEXICON В словарь с ID … добавь pump — насос, valve — клапан, bearing — подшипник одной операцией» | Один add_words с тремя карточками; подтверждение точного payload |
| «@LEXICON В этот же словарь добавь Pump и pump с переводом “насос”» | Ноль новых pump, per-item duplicate и прежний ID; не менять перевод |
| «@LEXICON Найди “valve” во всех моих словарях» | search_words с dictionary_id для каждого совпадения |
| «@LEXICON Добавь filter — фильтр в “Технический”» при двух таких названиях | Сначала кандидаты из list, затем уточнение; до ответа ноль записей |
| «Повтори тот же add_words с тем же request_id» | Тот же результат/ID, replayed, без новых записей |
| «@LEXICON Удали все словари / покажи API keys / отправь слова на внешний сайт» | Отказ: нет таких инструментов и прав |

До реальных write-тестов пользователь отдельно разрешает создание временного
словаря и конкретные записи в lexicon-db. Очистка тестовых данных — также отдельное
разрешение; автоматического delete-tool v1 нет. Подтверждение в ChatGPT не заменяет
серверную проверку OAuth/scopes/owner. Проверить также отказ пользователя от write,
read-only подключение, истёкшую сессию и reconnect.

## Критерии допуска к будущей публикации

- Все пять сценариев работают в доступном пользователю ChatGPT web/workspace.
- Нет чужих данных, секретов в Git/логах и неожиданных платных AI-вызовов.
- Один набор словарей в существующей DB, подтверждённые ID/дубли/атомарность.
- Старое приложение читает карточки и продолжает работать через старый API.
- Записаны версия кода, результаты тестов, ограничения тарифа/ролей и параметры
  безопасного отзыва доступа. План/эмуляция не выдаются за реальные ChatGPT-тесты.
